# «Расчёт» — лицензируемый staging и сохранность книги

Серверный контракт Ventry Delivery PR #77, main 769726510cebba89f85754e135a317c095f69a62. Тарифы уже утверждены; отдельный 24h код активации, trial начинается при активации, обновляемый offline lease до 72h. Production rollout пока не разрешён автоматически.

## Реализовано
- REQ-LIC-01. Изолированная сборка dev.ventry.raschet.licensedstaging только при паре Gradle properties raschetLicensePublicKey (raw 32-byte public key hex) / raschetLicenseOrigin (loopback HTTP explicit port). Без параметров существующие debug/release не блокируют записи и не имеют активного endpoint; release не содержит тестовый pin. Это намеренный этап перехода, не коммерческий выпуск.
- REQ-LIC-02. Экран «Настройки → Лицензия»: одноразовый код, сохранённый повтор, обновление, статус/срок. Keystore AES-GCM и AtomicFile в noBackupFilesDir, refresh secret генерируется до POST, не логируется/не попадает в URL или JSON-копию. При явной новой активации предыдущее локальное разрешение заменяется; книга не меняется.
- REQ-LIC-03. Ed25519 через lightweight Bouncy Castle (без регистрации провайдера); pinned raw public key, SHA-256 key ID, точные подписанные payload bytes, типы/состав claims, issuer/product/package/installation, revision/time/lease, отказ неизвестному ключу. Не использовать response key как доверенный. HTTPS production пока не включён в staging build.
- REQ-LIC-04. Проверка нового долга в общей insertEntry LedgerStore, внутри транзакции. Обычная и itemized покупка и датированная запись идут через эту границу. Просмотр, оплата, исправление существующего, отмена и восстановление остаются доступны. Импорт — восстановление книги, не операция продажи; не позиционировать защиту как невозможность подделки на модифицированном клиенте. No schema migration.
- REQ-LIC-05. Срок проверяется по signed time, monotonic elapsedRealtime и wall clock. После перезагрузки требуется сеть (boot count недоступен → fail closed для новых долгов); смещение часов назад не продлевает монотонный lease. На восстановлении сети автоматический refresh при входе (до одного фонового запроса в 15 минут), также ручной refresh. Авторизованный 404 очищает локальное разрешение, transient отказ сохраняет до expiry. Истёкшие/повреждённые claims запрещают только новые долги.
- REQ-LIC-06. Unit policy tests и отдельный CI с настоящим Rust/PostgreSQL Delivery из фиксированной ревизии, подписанной trial activation через UI эмулятора, проверкой обычной записи, отказа, оплаты, JSON restore, подмены подписи и смены boot. Ключ генерируется только на runner, тестовый APK не публикуется: endpoint локален и ключ одноразовый. Тестируется отдельная БД, не пользовательская книга. Обычные CI gates сохраняются.

## До commercial rollout
Нужен постоянный отдельный production Ed25519 key, защищённый public HTTPS origin и закреплённый публичный pin, план ротации/backup, проверенная установка обновления поверх подписанного RC, принятие условия офлайн-срока и миграции действующих пользователей. Публичный RC всё ещё без проверки подписки; подписка не защищена от модификации открытых исходников. Никаких production ключей, реальных платежей, обновления публичного APK или развёртывания на VDS в этой ветке.

## Устойчивое восстановление активации (следующая ревизия)

Новая активация транзакционно хранит отдельный pending_refresh в том же зашифрованном AtomicFile. Действующая лицензия и её credential не заменяются до проверки нового Ed25519 ответа. Старый v1 pending без поля pending_refresh читается с прежним refresh. При повторе сначала проверяется новый refresh secret: если сервер уже зафиксировал активацию, восстанавливаем ответ даже после истечения кода. Только явный JSON 404 activation_unavailable считается отказом; обычный 404 прокси/сети сохраняет состояние. При однозначном отказе кандидата прежняя действующая лицензия сохраняется; новый код нельзя подменить до завершения ожидающего запроса. При потере сети ограниченный прежний lease остаётся доступен, но не продлевается. Необратимая потеря файла/Keystore по-прежнему требует администратора. Реальный Android тест проверяет ошибочный код, восстановление ответа по refresh после имитации потери результата, прежний срок trial и неизменность книги.

Если расшифрованная локальная запись содержит испорченный cached envelope, новый подписанный и свежий ответ может восстановить доступ через прежний refresh. До этого новые долги блокируются; испорченный envelope не используется как доверенный baseline. Сценарий проверяется инструментальным тестом. Потеря самого Keystore/refresh по-прежнему требует администратора.
