# Экспериментальное серверное ядро

Это изолированный прототип доменной модели, не сетевой сервис и не готовая авторизация. Node.js 24 с `node:sqlite`, без сторонних зависимостей. `actor` должен предоставляться проверенным серверным провайдером идентификации; пользовательскому вводу доверять нельзя. Интеграция с интерфейсом отсутствует. Не использовать с реальными клиентами и не публиковать как production API.

Доступные операции: создать магазин и владельца, добавить участника владельцем, создать клиента, записать долг/оплату, просмотреть журнал, создать копию SQLite. Идентификатор операции и хеш полезной нагрузки позволяют повторить идентичную операцию без двойной записи; тот же идентификатор с изменённой нагрузкой отклоняется. Транзакция проверяет членство и остаток перед записью. Суммы — целые копейки.

Запуск изолированных тестов: `node --test tests/*.test.js`. Тест создаёт временную базу, два магазина и фиктивные личности, проверяет роли, границы магазинов, повтор операции, запрет переплаты и чтение восстановленной копии, затем очищает временный каталог.

Остаются: проверенная аутентификация и доступ по сети; управление участниками и отзыв; журнал событий участников; отмены и совместимость с локальным форматом v1/v2; очередь без сети, конкурентная синхронизация, конфликт данных; регулярное резервирование, проверка целостности и восстановление; шифрование, эксплуатационные настройки, миграции и негативные интеграционные тесты. SQLite в этой изолированной проверке не является решением для распределённой многосерверной системы.


## Тестовый сетевой слой

`server/http.js` — HTTP API, `server/auth.js` — адаптер OAuth 2.0 token introspection, `server/start.js` — локальная точка запуска. Все запросы к данным, кроме `/health`, требуют bearer access token; токен проверяется у настроенного поставщика на каждом запросе. Требуются активный токен, совпадающие issuer и audience, неистёкший срок и идентификатор пользователя. Сеть по умолчанию слушает только `127.0.0.1`, introspection URL требует HTTPS; исключение для HTTP loopback доступно только при явной передаче опции в тестах.

Конфигурация процесса: `IDENTITY_INTROSPECTION_URL`, `IDENTITY_ISSUER`, `IDENTITY_AUDIENCE`, `IDENTITY_CLIENT_ID`, `IDENTITY_CLIENT_SECRET`, `LEDGER_DATABASE`, опционально `PORT`. Реальных значений, ключей или базы в репозитории нет. Запуск: `node server/start.js` после настройки из доверенной среды. Клиентский секрет должен храниться в менеджере секретов.

Маршруты: `POST /shops`, `POST /shops/:shop/members`, `DELETE /shops/:shop/members/:user`, `POST /shops/:shop/clients`, `POST /shops/:shop/entries`, `GET /shops/:shop/entries`. Добавление и отзыв продавцов разрешены владельцу. Удаление владельца не поддерживается. Механизм добавления участника пока принимает его идентификатор провайдера напрямую; безопасные приглашения и управление пользователями не реализованы.

`tests/http.test.js` поднимает настоящий HTTP-сервер и локальный имитатор провайдера с вымышленными токенами. Реальный провайдер, его настройки выдачи и отзыва токенов, TLS, внешний прокси, лимиты частоты запросов и производственная эксплуатация не проверены. Без этого и без миграции, безопасного развёртывания и проверки на границах доверия продукт не готов для настоящих данных. Отдельного входа/регистрации и интерфейса у API нет.

## Кандидат для Amvera

Корневой `amvera.yaml` задаёт Node.js 24, запуск `server/start.js`, порт 80 и постоянный каталог `/data`. В Amvera при `AMVERA=1` сервер слушает `0.0.0.0`; в обычном локальном режиме — только `127.0.0.1`. Если `PORT` задан вручную, он должен совпадать с `run.containerPort`. База задаётся абсолютным путём через `LEDGER_DATABASE`, например `/data/dolg-book.sqlite`. В Amvera без настроенного провайдера открывается только локальный браузерный прототип; защищённый API остаётся недоступен. При частично заполненной конфигурации запуск завершается ошибкой. Если LEDGER_DATABASE не задан, используется /data/dolg-book.sqlite. Токены и клиентские секреты задаются в хранилище секретов платформы, а не в Git.

Тот же процесс отдаёт локальный веб-прототип и ограниченный список его статических файлов. Его учёт по-прежнему работает через localStorage конкретного браузера и не подключён к серверному API; публикация приложения не создаёт общую книгу. `/health` проверяет ответ процесса, не работоспособность провайдера или сохранность базы.

Проверка: `npm test` запускает реальный сервер в отдельном процессе с временной базой и фиктивной конфигурацией, проверяет загрузку HTML/JS/CSS, HTTP 401 без токена и сетевую привязку Amvera. Реальная платформа Amvera, реальный провайдер авторизации, доступность в браузере и сохранение базы между перезапусками платформы не проверены. Запускать только с тестовыми данными и после настройки защищённого провайдера.

### Состав сборки Amvera

`node scripts/build-amvera.mjs` формирует `amvera-dist` из явно перечисленных файлов; команда отказывается перезаписывать немаркированный каталог. Сборка исключает Markdown, тесты и `project-source.zip`, а ссылка в создаваемом HTML ведёт на GitHub. `amvera.yaml` передаёт в runtime только `amvera-dist/*`. Ветка `amvera-test` содержит только файлы для сборки и запуска; полная документация остаётся в ветке разработки. Локальные тесты проверяют собранный состав и запуск; результат на Amvera необходимо подтвердить после фактической сборки.

## Админка подписок

Страница `/admin/` включается при настройке `LEDGER_ADMIN_SUBJECT`. Укажите точный идентификатор `sub` учётной записи оператора у настроенного поставщика токенов. Для тестового входа используется access token этого оператора. Токен остаётся в памяти страницы до выхода или закрытия вкладки. Поставщик должен выдать токен с ранее настроенными issuer и audience.

Оператор находит магазин по номеру из `GET /shops`. После ручной проверки оплаты он вводит её уникальный номер и подтверждает доступ на календарный месяц. При действующей подписке месяц добавляется к текущему сроку, иначе отсчёт начинается с подтверждения. Граница месяца рассчитывается по UTC, интерфейс показывает время по Москве. Повтор одного номера оплаты возвращает текущий срок, а использование номера для другого магазина отклоняется. После изменения срока в другой вкладке требуется обновить карточку перед новым подтверждением.

При включённой админке API разрешает создание клиентов и запись долгов или оплат только при действующей подписке. Чтение книги доступно её участникам и после окончания срока. Интеграционные тесты запускаются командой `npm test`. Публичное веб-демо использует собственные локальные данные.

### Вход через Keycloak и общая книга

С настройкой `LEDGER_BROWSER_ORIGIN` клиент открывает `/book/`, а оператор — `/admin/`. Обе страницы используют вход через Keycloak. URL задаётся как точный внешний HTTPS origin, без пути и завершающего слеша. Вход выполняет сервер по Authorization Code с PKCE. В браузере остаётся идентификатор сессии в защищённой cookie. Сессия истекает вместе с access token, максимум через 30 минут. Пока сессии хранятся в памяти, для перезапуска или смены экземпляра требуется войти заново.

1. В Keycloak создайте realm для «Расчёта». Создайте клиент OpenID Connect с включёнными **Client authentication** и **Standard flow**, S256 PKCE и точным **Valid redirect URI** из внешнего origin с путём `/signin/callback`. Direct access grants и wildcard redirect пропустите. Для пилота создайте аккаунты покупателей и отдельную учётную запись оператора.
2. Настройте в Keycloak отображение **Audience** так, чтобы выбранная аудитория API присутствовала в `aud` ответа introspection. Используйте `sub` оператора из проверенного ответа introspection, а не отображаемый логин. При необходимости отображения почты убедитесь, что Keycloak возвращает `email` и `email_verified`.
3. В настройках хостинга задайте `IDENTITY_ISSUER` как точный HTTPS URL realm, `IDENTITY_INTROSPECTION_URL` из его discovery, `IDENTITY_CLIENT_ID`, `IDENTITY_AUDIENCE`, `LEDGER_ADMIN_SUBJECT` и `LEDGER_BROWSER_ORIGIN`. `IDENTITY_CLIENT_SECRET` задайте как секрет среды. Для Amvera укажите `LEDGER_DATABASE=/data/dolg-book.sqlite` и одну реплику. Публичный трафик принимается через HTTPS-прокси хостинга.
4. После запуска проверьте `/health`. Создайте тестовый магазин под покупателем, убедитесь, что запись закрыта, подтвердите вымышленную оплату под оператором, запишите тестовый долг и оплату, проверьте остаток после повторного входа. Проверьте восстановление копии и ограничения запросов на хостинге до приёма реальных данных.

Справка: [Keycloak OIDC](https://www.keycloak.org/securing-apps/oidc-layers), [Amvera — секреты](https://docs.amvera.ru/applications/configuration/variables.html), [Amvera — постоянное хранилище](https://docs.amvera.ru/applications/storage.html).
